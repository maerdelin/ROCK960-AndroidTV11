# ROCK960 Android 11 bring-up closure — 2026-08-20

This file records the real build/repack findings that must not be lost between clean
checkouts. It is deliberately limited to source and packaging facts that were verified
while producing the first ROCK960 Android 11 test image from the ASUS/Tinker Board 2
Android 11 2.0.8 BSP.

## Kernel target and toolchain result

The verified kernel target is:

```text
rk3399-rock960-ab-android
```

The build produced a working kernel image and DTB after the fixes below. The controller's
normal build must apply the same fixes before kernel compilation.

## Fix 1 — stale `&vpu` node

ASUS 2.0.8's pinned ROCK960 DTS contains an `&vpu` node, while the kernel tree exposes the
video blocks under different symbols. DTC failed with:

```text
Label or path vpu not found
FATAL ERROR: Syntax error parsing input tree
```

`tools/make_rock960_android_dts.py` now removes exactly one expected stale `&vpu` block
while generating `rk3399-rock960-ab-android.dts`.

## Fix 2 — Tinker MCU variables in `panel-simple.c`

With ROCK960's config, two variables used only by the Tinker MCU path were compiled while
`CONFIG_TINKER_MCU` was disabled. The ASUS kernel treats warnings as errors. The validated
fix guards these variables with `#if defined(CONFIG_TINKER_MCU)`.

## Fix 3 — Tinker AT24 Ethernet MAC path

`drivers/net/ethernet/stmicro/stmmac/eth_mac_tinker.c` tried to read the Ethernet MAC from
a Tinker Board AT24 EEPROM path which is not the ROCK960 board contract. The validated fix
zeros the buffer and returns, allowing the normal stmmac/platform fallback to provide the
address.

The exact source diff for fixes 2 and 3 is:

```text
patches/rock960-kernel-build-fixups.patch
```

`scripts/apply-kernel-fixups.sh` is the canonical idempotent applier and is called by
`scripts/apply-port.sh`.

## Boot image validation performed

The official ASUS 2.0.8 raw image's `boot` GPT partition was extracted and used as the
repack template. The generated ROCK960 test boot passed these checks:

```text
ASUS ramdisk                 byte-identical
boot image header version    unchanged (v2)
Android OS version           unchanged (11.0.0)
OS patch level               unchanged (2021-08)
command line                 unchanged
new kernel                   equals built ROCK960 Image
original kernel              replaced
ROCK960 DTB/resource         regenerated for rk3399-rock960-ab-android
```

`scripts/repack-asus208-boot.sh` preserves and rechecks this contract.

## Safe RKUpdate packaging policy used for first boot

The first test `update.img` was packed with ASUS 2.0.8 `afptool` and `rkImageMaker`. The
package contains the Android partitions needed for the test and an RK3399
`MiniLoaderAll.bin` required by RKUpdate/RKDevTool.

For first-boot safety, the package-file deliberately omits persistent:

```text
uboot.img
trust.img
```

This keeps the existing ROCK960 persistent boot chain in place while Android/kernel bring-
up is still being validated. The compiled U-Boot/trust outputs are kept only as debug
artifacts in the full build.

`scripts/pack-safe-update.sh` is now the canonical packer. It:

1. builds the pinned RK3399 MiniLoaderAll from `rkbin/RKBOOT/RK3399MINIALL.ini`;
2. generates package-file entries only for images present in the flash payload directory;
3. rejects `uboot.img` or `trust.img` if accidentally placed in that directory;
4. packs with `afptool` + `rkImageMaker -RK330C`;
5. unpacks the inner firmware and compares `boot.img` byte-for-byte;
6. writes a SHA-256 file for the final update image.

## Exact minimal-current workflow

To reproduce the same prebuilt-user-space experiment rather than doing a fresh full Android
build:

```bash
./scripts/repack-asus208-boot.sh \
  --firmware /path/Tinker_Board_2-Android11-v2.0.8-20220503.img \
  --out /path/rock960-test-boot.img

./scripts/repack-asus208-current.sh \
  --firmware /path/Tinker_Board_2-Android11-v2.0.8-20220503.img \
  --boot /path/rock960-test-boot.img \
  --out /path/ROCK960-Android11-v2.0.8-update.img
```

The second script derives `parameter.txt` from the official ASUS GPT and extracts exactly:

```text
misc
dtbo
vbmeta
recovery
baseparameter
super
```

It inserts the verified ROCK960 boot image and invokes `pack-safe-update.sh`.

## What is not yet hardware-validated

A successful compile/package is not equivalent to full hardware validation. The first
physical-board test must still establish at least:

- U-Boot handoff into the ROCK960 kernel;
- HDMI display;
- eMMC and USB;
- Ethernet;
- AP6356S Wi-Fi firmware/NVRAM;
- Bluetooth;
- HDMI/audio path.

Camera, USB-C DisplayPort, MIPI-DSI and MIPI-CSI are intentionally outside the first-boot
claim.
